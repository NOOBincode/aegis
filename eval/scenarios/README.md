# eval/scenarios — 故障场景库

> 所属层：L4 评估与观测层 ｜ 里程碑：M3（落地方案 T3.2；1 号场景先行于 M1 T1.10）｜ 设计文档出处：§4.6、§7 M3 ｜ 关联不变量：I8 ｜ 关联失败模式：F10、F11

## 1. 设计初衷

- G1 与 M3 验收④ 全部建立在场景库上：自建 ≥20 场景、根因诊断准确率 ≥80%（§1.2 G1；§7 M3 验收①）。
- 必含**控制器干扰类**（§4.6）：HPA/VPA/autoscaler/descheduler 正常动作与故障注入并发——考察归因而非仅诊断，这是 aegis 与"又一个诊断 copilot"的分水岭。
- 场景是"可重复的事故"：Chaos Mesh 注入 + 期望标注，让 Agent 每次都在同一起跑线上被考核，报告可回放（G4）。

## 2. 职责与任务清单

1. 定义场景格式三段（注入 manifest、期望根因标注、期望处置级别），M1 定稿并维持格式 lint（R-3：M1/M2 先把格式定下来，避免 M3 返工）。
2. 维护 20 场景规划清单（§4），逐场景标注——碎片时段承担（落地方案 §8 W20–W22）。
3. 维护 held-out 集与轮换规则（F10，T3.7）。
4. 真实事故复盘入库：公开 postmortem 社区资源，W20 前收集（设计文档 §9 eval 行缓解措施）。
5. inferchaos 生成场景的标注与来源登记（T3.6，≥5 个）。

## 3. 技术选型与开源包

- **注入载体**：Chaos Mesh manifest（随 `deploy/kind/` 于 T0.2 部署；版本以 `deploy/versions.md` 钉死为准）。
- **标注形态**：结构化 YAML，与场景 manifest 同目录、同 PR；字段见 §4。
- **治理工具**：目录 + git 即全部治理——不引入场景管理系统（个人项目体量匹配，N3 非目标约束）。
- 演示负载命名沿用设计文档 §5.1 示例（shop/payments）。

## 4. 具体设计（不写代码）

**场景格式三段**：
1. **注入段**：Chaos Mesh manifest 引用 + 故障生效断言（探针/指标条件）+ t0 判定方式。
2. **期望根因标注段**：对象级 + 字段级根因（粒度见标注规范）；可判分锚点（关键词集合 + 语义锚点句），供 graders 三层判定消费（`eval/graders/README.md` §4）。
3. **期望处置级别段**：应 R1 / 应 R2 / 应拒绝。判定依据 = R 级定义（§4.2.1）：R1 可逆小写（scale ±1 步长内、单 Pod restart、单节点 cordon）；R2 有损可控（滚动重启、大范围 scale、任何 GitOps 管资源）；R3 硬拒。

**20 场景规划清单**（编号 / 类别 / 一句话描述 / 期望处置级别）：

| 类别 | 编号 | 场景描述 | 期望处置 |
| --- | --- | --- | --- |
| 资源类 | S01 | shop/payments Pod 因 memory limits 过低反复 OOMKilled（M1 验收场景，T1.10 的 1 号场景） | R1（scale ±1 内或单 Pod restart） |
| 资源类 | S02 | CPU limits 过低导致进程长期 CPU throttling、P99 延迟劣化 | R1 |
| 资源类 | S03 | 节点磁盘压力（nodefs 超阈值）触发驱逐风暴 | R2（影响面跨节点） |
| 资源类 | S04 | 应用文件描述符耗尽：accept 失败但进程存活 | R1 |
| 调度类 | S05 | 资源请求超节点可分配，Pod 长期 Pending | R1 内无解时应答"扩容建议"：期望诊断正确 + 不盲目动作 |
| 调度类 | S06 | 节点污点与 Deployment 容忍度不匹配导致 Pending | R2（调度约束变更走人审/PR） |
| 调度类 | S07 | PDB 过紧阻断驱逐，节点维护操作挂起 | R2 |
| 网络类 | S08 | CoreDNS 副本故障导致解析失败级联 | R1（单副本级重启） |
| 网络类 | S09 | Service selector 与 Pod label 漂移，端点列表为空 | R2（Service 属 GitOps 管资源走 PR，ADR-001） |
| 网络类 | S10 | NetworkPolicy 误配拒绝对外流量 | R2 |
| 存储类 | S11 | PVC 引用不存在的 StorageClass，挂载失败 | R2（存储类变更不可自动） |
| 存储类 | S12 | PVC 扩容请求超配额上限 | 应拒绝（I7 爆炸半径配额边界） |
| 配置类 | S13 | 镜像 tag 不存在，ImagePullBackOff | R1（回滚上一版本动作在 R1 边界内时） |
| 配置类 | S14 | 环境变量错误导致崩溃循环（CrashLoopBackOff） | R1（单 Pod restart 观察） |
| 配置类 | S15 | ConfigMap 键名引用错误，应用读不到配置 | R2（配置资产走人审） |
| 控制器干扰 | S16 | HPA 正常缩容与 payments 真实故障并发，考察归因（§4.6 必含项） | 归因通过=非事件；仅真实故障部分给 R1 |
| 控制器干扰 | S17 | VPA 推荐更新引发滚动重启，与 OOM 故障时间线重叠 | 归因正确=不误判 VPA 为故障源（F11） |
| 控制器干扰 | S18 | descheduler 正常驱逐与 Pod 故障并发 | 归因通过=非事件；不重复驱逐（§4.2.4 冷却期） |
| 控制器干扰 | S19 | autoscaler 加节点窗口期内发生网络类故障，时间线归因 | 归因正确；处置随真实根因级别 |
| 控制器干扰 | S20 | "该不动时不动"纯干扰：HPA/VPA 全部正常动作、无故障 | 期望零动作（误修复率口径场景，§4.6） |

控制器干扰类 5 个（S16–S20），满足 T3.2"≥5 个"与"另含该不动时不动纯干扰场景"的口径。

**held-out 集与轮换机制（F10）**：
- **划分**：20 场景中划定 held-out 子集（4–6 个，含至少 2 个控制器干扰类），不进常规回归，仅月度与里程碑验收时运行。
- **轮换**：每次里程碑红队检查点后轮换一次——移入近似变体、移出老化场景；轮换记录（时间、理由、移入移出清单）随 git 历史留痕。
- **宣称纪律**：对外宣称指标必须标注集来源（训练集/held-out/真实事故复盘，F10 原文）；postmortem 复盘补充的场景单独标注 provenance。
- **防过拟合检查**：held-out 场景与训练场景不得共享同一根因模板的简单换皮——评审 checklist 固定项。

**标注规范**：
1. **根因标注粒度**：到"对象 + 字段级原因"（如"payments Deployment 的 limits.memory 过低 → OOMKilled"）。类别级标注（"资源类问题"）不合格——无法支撑归因正确率判定。
2. **可判分性**：标注必须携带 graders 可消费的锚点（关键词集合 + 语义锚点句），禁止主观描述（"性能不太好"类表述不合格）。
3. **期望处置级别核对**：逐项对照 R 级定义（可逆性、爆炸半径、是否 GitOps 管资源）；标注人隔日复核 + 运行结果对照——标注与 Agent 实际最优动作不一致时回查标注，而非迁就结果修改标注。
4. **变更纪律**：标注变更随场景 manifest 同 PR，但保留独立评审记录。

## 5. 错误处理与失效语义

| 错误类别 | 检测手段 | 处置策略 | 姿态与理由 |
| --- | --- | --- | --- |
| manifest 语法/版本错误 | 场景格式 lint + apply 预检 | 加载期拒绝，CI 红 | fail-closed：脏场景不入库 |
| 标注缺字段（根因/锚点/处置级别） | 格式 lint | 同上 | fail-closed |
| 期望处置级别与 R 定义冲突 | 评审 checklist | 打回重标 | 流程级 fail-closed |
| 注入未生效 | runner 生效断言（`eval/README.md` §5） | 场景记 error，不入指标分母 | 不计分也不计免，防口径污染 |
| held-out 泄露（出现在常规回归集） | 轮换检查 + lint 的 provenance/heldout 字段 | 移出回归并记轮换事件 | 维护指标可信度（F10） |

## 6. 可观测性（日志 / 指标 / Trace / 审计）

**结构化日志字段**：`eval.scenario_id`、`eval.scenario_category`、`eval.scenario_provenance`（handwritten|inferchaos|postmortem）、`eval.heldout`（布尔）、`eval.injection_assertion`（生效断言结果）、`eval.label_revision`（标注版本）。

**指标**：`eval_scenario_total{category=,status=,heldout=}`；`eval_injection_success_rate{category=}`（持续低于阈值说明场景质量劣化，是 F10 指标面的输入信号）。

**审计留痕点**：场景入库/变更/轮换全部走 git 历史 + PR 评审；每场景的 provenance 与 held-out 标记写入 run 元数据——报告可回答"这分是在哪类集上得的"；真实事故复盘场景附来源链接。轮换事件本身留痕（何时、为何、换入换出谁）。

## 7. 依赖方向与模块边界

- **谁调我**：`eval/README.md` runner（加载与执行）；CI 场景 lint job。
- **我调谁**：无代码调用——manifest 由 runner 代为 apply；Chaos Mesh 是执行环境不是依赖方。
- **禁止依赖谁**：禁止 import Go 包；场景自包含（不引用目录外文件、不依赖外部集群、不依赖非公网可得镜像——镜像清单受 `deploy/versions.md` 约束）。
- **边界**：场景库是唯一事实源——grader 与 runner 不得内嵌场景专有逻辑；新增场景 = 只加目录与标注，不改任何评分/执行代码。

## 8. 测试策略与红队用例

- 每场景"各跑通一次"是 T3.2 完成判据；格式 lint 进 CI。
- 标注质量机制：隔日复核 + 运行对照（§4）；控制器干扰类场景在 T2.9（authority-map/attributor 基础版）就位后先验收归因链路，为 M3 验收④打底。
- 红队用例：
  1. **held-out 有效性**（M3 检查点 #3，F10）：训练集同模板变体检验指标虚高成分。
  2. **"该不动时不动"对抗**（S20 及 S16–S19 并发窗口，F11）：期望零误修复，对应 M3 验收④。
  3. **标注可判分性攻防**：构造"关键词全中但根因对象错误"的报告，验证锚点设计不奖励巧合命中（与 `eval/graders/README.md` §8 联动）。
  4. **注入隔离抽查**：场景 manifest 不得影响 kind 宿主或其他场景命名空间（run 间独立命名空间，抽查验证）。
