# eval/graders — 评分器设计

> 所属层：L4 评估与观测层 ｜ 里程碑：M3（落地方案 T3.3）｜ 设计文档出处：§4.6 ｜ 关联不变量：I8 ｜ 关联失败模式：F10、F11

## 1. 设计初衷

- 四大一等指标（诊断准确率/归因正确率/误修复率/MTTR）必须**可判分、口径公开、可复核**——T3.3 完成判据即"报告产出，指标口径文档化"（本文件即口径文档）。
- 归因正确率与误修复率与诊断准确率**并列一等**（§4.6）：只考"诊得准"不考"不乱动"，等于放纵 F11（控制器正常行为被误判为故障）。
- 评分器自身也是被考核对象：判定层级、推翻记录、口径变更全部留痕，防"评分标准漂移导致指标不可比"（F10 的变体风险）。

## 2. 职责与任务清单

1. 四指标判定实现与口径维护（本文件 §4 为唯一口径源）。
2. 根因命中三层判定：关键词锚点层 / 语义匹配层 / 人工抽检层。
3. 报告生成：机器可读 JSON（供 CI 门禁 diff 与基线对比）+ 人读 markdown（同一数据源渲染，杜绝两套口径）。
4. 人工抽检工作流支持（第三层判定：队列、表单、推翻记录）。
5. 评分一致性自测：黄金样例对随 grader 改版回归。

## 3. 技术选型与开源包

- **语言**：Python，与 eval 同世界；不引入评分专用服务。
- **语义匹配层**：具体技术选型（embedding 相似度或其他）在 T3.3 实施时确定，须过依赖评审（理由 + license，仅 MIT/Apache-2.0/BSD，对齐 aegis-go-quality 依赖纪律的 Python 侧口径）；本文件不预钉。
- **人工抽检层**：无技术依赖——判定录入表单，结果归档进 run 目录。
- **LLM-as-judge 默认不引入**：成本、可重复性、注入面三重顾虑；如未来引入须先评审并过 I8 口径变更流程（§6 审计节）。

## 4. 具体设计（不写代码）

**四指标判定方法**：

| 指标 | 判定方法 | 口径要点 |
| --- | --- | --- |
| 诊断准确率 | Agent 诊断报告的根因 vs 场景标注根因，三层判定（下述） | 分母=有效场景数（infra_error/error 剔除）；命中 = 对象维度 + 原因维度双一致 |
| 归因正确率 | 干扰并发类场景（S16–S19）中，Agent 将控制器正常行为正确归因为非事件的比例 | "归因通过=非事件"判定正确（F11）；把 VPA 正常重启误判为故障源 = 归因错误；分母=干扰并发类有效场景 |
| 误修复率 | "该不动时不动"场景（S20）及干扰并发窗口内的误动作数 | 任何不必要写动作（含对非根因对象的处置）计误动作；期望恒 0（M3 验收④）；分母=干扰类场景数 |
| MTTR | t0 = 故障生效断言通过时刻；t1 = 恢复性 ChangeRequest 进入 Committed 时刻（§5.1 状态机终态） | 仅诊断无处置的会话 t1 不存在，该场景 MTTR 记 n/a 不进均值——只统计真实处置闭环；若回滚，t1 = 回滚完成且服务恢复时刻 |

**根因命中三层判定**：
1. **L1 关键词/锚点层**：标注携带的关键词集合与字段锚点在报告中命中；对象名 + 原因词**双命中**才算——防单维度巧合（"提到 payments 就算命中"不合格）。
2. **L2 语义匹配层**：报告根因句与标注语义锚点句的相似度 ≥ 阈值判命中；阈值在基线建立时校准并记录（写入口径修订历史）。
3. **L3 人工抽检层**：每 run 抽检固定比例（默认 10%；held-out 场景 100% 人工复核）。L3 结论可推翻 L1/L2，推翻记录留痕；推翻率本身是 grader 质量指标（§6）。

判定结论三值：`hit` / `miss` / `unclear`——unclear 进人工队列，不自动算 miss（方向性：宁可低估不可高估，见 §5）。

**报告的机器可读格式**（result.json 语义结构）：
- 头部：`run_id`、`config_hash`（prompt 版本、模型通道、场景集版本）、`baseline_ref`。
- `metrics`：四指标值 + 各指标分母明细（有效场景数、n/a 数）。
- `per_scenario[]`：`scenario_id`、`category`、`heldout`、四指标分项、`judge_level`（L1/L2/L3）、证据引用（DecisionRecord / run 内路径）。
- `comparison`：vs 基线的 delta（per 指标 + per 场景）——`eval/regression/README.md` 阻断规则的唯一消费面。

人读 markdown 由同一数据源渲染，禁止手工编辑报告数值。

## 5. 错误处理与失效语义

| 错误类别 | 检测手段 | 处置策略 | 姿态与理由 |
| --- | --- | --- | --- |
| 证据缺失（DecisionRecord 缺失/报告未产出） | 评分前置检查 | 该场景判 fail 并标 missing_evidence | fail-closed：证据不全不得豁免指标——否则"不回答"成为逃避判分的通道 |
| 语义匹配层不可用 | 层健康检查 | 降级为仅 L1 关键词层；该 run 标 `semantic_coverage=false`；L1 未命中且语义不可用者进人工队列 | 评分可降级，**不得伪造命中**：宁可低估不可高估——门禁方向性选择误放 > 误杀（F10 环境下宽容忍=给虚高开后门） |
| 人工抽检积压（L3 队列超期） | 队列长度监控 | run 报告标"抽检未完成"，门禁按未完成不放行处理 | fail-closed 于发布 |
| 口径自相矛盾（同场景两指标判定冲突） | 评分自检 | run 失败不上报告 | 防脏数据进基线 |
| grader 自身异常 | 错误面 | 同 `eval/README.md` §5：run 失败，不更新基线 | fail-closed |

## 6. 可观测性（日志 / 指标 / Trace / 审计）

**结构化日志字段**：`eval.grader`、`eval.metric`、`eval.scenario_id`、`eval.judge_level`（L1/L2/L3）、`eval.judge_result`（hit/miss/unclear）、`eval.judge_input_hash`（判定输入哈希，支持重算复核）、`eval.override`（L3 推翻记录，含理由与判定人）。

**指标**：`eval_grade_total{metric=,result="hit|miss|unclear"}`；`eval_human_review_queue_depth`；`eval_override_rate`（L3 推翻率——grader 质量信号，持续偏高说明 L1/L2 判定失准）。

**Trace**：span `eval.grade`（属性：scenario_id、metric、judge_level、judge_result），作为 `eval.scenario.<id>` 子级（span 树约定见 `eval/README.md` §6）。

**审计留痕点**：判定输入哈希 + 三层判定全记录 + 人工抽检表单归档进 run 目录——评分可完整重算（I6 决策可回放精神在 L4 的落地）；口径文档（本文件）变更走 PR 评审，并同步说明基线重评策略（口径变了，旧基线是否重评、如何重评）。

## 7. 依赖方向与模块边界

- **谁调我**：`eval/README.md` runner（评分阶段唯一调用方）；CI 门禁（消费 result.json 的 comparison，不调用 grader 内部）。
- **我调谁**：场景标注（只读）；run 目录内 Agent 产出（只读——诊断报告、DecisionRecord）；（选型确定后）语义匹配库；人工抽检经表单录入。
- **禁止依赖谁**：禁止 import Go 包；评分**不得反向调用被测 Agent 或活会话**——评分输入仅来自归档证据，防评分器被会话内注入影响（评分侧也是攻击面）；引入 LLM-as-judge 类依赖前须评审（§3）。
- **边界**：grader 不认识具体场景——所有场景特异性知识在标注里（`eval/scenarios/README.md` §4 锚点设计）；grader 只实现通用判定层，新增场景零 grader 改动。

## 8. 测试策略与红队用例

- **黄金样例对**：每指标维护"已知命中/已知未命中"报告对各一组，grader 改版必跑（评分一致性回归）。
- **口径回归**：口径文档变更时，历史 run 重评分一致性检查（同输入同输出）。
- 红队用例：
  1. **刷分攻防**：构造关键词全中但根因对象错误的报告，验证双维度命中要求（L1 不奖励巧合）。
  2. **语义层失效演练**：语义服务宕机时验证降级路径、`semantic_coverage=false` 标记，且降级 run 不得静默升格基线（§5）。
  3. **误修复口径攻防**：干扰窗口内"做了无害小动作"（对非根因对象 restart）必须计误动作——口径不认"无害"（F11：无动作优于乱动作）。
  4. **MTTR 口径攻防**：注入后 Agent 秒回"已修复"但 ChangeRequest 未达 Committed 的会话不得记 t1——终点以 CR 状态机为准（§5.1 状态定义，见 `internal/controller/README.md`）。
  5. **unclear 滥用攻防**：构造模糊报告试探 unclear 是否被当作免死——unclear 进人工队列且计入分母（§4 口径）。
