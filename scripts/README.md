# scripts — 自动化脚本规范

> 所属层：跨层工程基座（自动化载体）｜ 里程碑：Phase 0（T0.2，W2）建立，红队与演示脚本随里程碑演进 ｜ 设计文档出处：§3.2 跨平台约定 ｜ 关联不变量：I10（失败语义）｜ 关联失败模式：F14（在途恢复演练）、F7（复位留痕）

## 1. 设计初衷

脚本是把"环境即代码"变成可执行动作的唯一通道：Makefile 薄封装 + `scripts/*.sh` 承载全部自动化（落地方案附录 B-1）。设计初衷三条：

1. **一份脚本两处执行**：本地 WSL2 与 CI 共用同一份脚本，kind/helm/kubectl 的安装步骤禁止写第二份（附录 B-4）。
2. **失败要响**：errexit、诊断输出、非零退出——与 I10 同源的工程表达：安全组件的故障不能静默，工程脚本也一样。
3. **可重入**：个人项目频繁重建环境，每个脚本必须幂等，连续执行两次结果一致。

## 2. 职责与任务清单

| 脚本/目录 | 职责 | 对应任务/里程碑 |
| --- | --- | --- |

## 3. 技术选型与开源包

- bash-only：PowerShell/BAT 不进关键路径（附录 B-1）；CI 步骤显式 `shell: bash`（aegis-ci）。
- 外部二进制（docker/kind/kubectl/helm）版本以 `deploy/versions.md` 为准，脚本启动时校验。
- `.gitattributes` 钉 `*.sh` 为 LF（附录 B-2），杜绝行尾引发的行为差异。

## 4. 具体设计（不写代码）

### 4.1 脚本骨架四要素

1. **严格模式**：errexit（任一命令失败即停）、pipefail（管道失败传播）、nounset（未定义变量即错）。语义：绝不允许"前半失败后半照跑"。
2. **统一日志**：每行带时间戳与 script_name、step、result 字段；同时输出人可读摘要。
3. **幂等可重入**：每个步骤先检测现状再决定创建/跳过/重建；连续执行两次结果一致。
4. **失败诊断**：errexit 触发时捕获失败命令上下文，输出诊断包（docker/kind/组件状态、最近日志尾部、版本表实装比对），然后非零退出。

### 4.2 参数契约（名称 + 职责 + 入出参语义）

| 脚本 | 关键入参 | 退出码语义 | 出参（摘要） |
| --- | --- | --- | --- |
| env-up.sh | 可选组件白名单（只装部分组件） | 0 全绿；2 前置缺失；3 超时；4 环境不可用；1 其他失败 | 健康摘要（组件/版本/状态/端口） |
| env-down.sh | 强制标志 | 0 清理干净；非 0 有残留需人工 | 残留清单 |
| runsc-smoke.sh | 集群名 | 0 通过；非 0 按降级链处置 | 平台结论（ptrace/KVM/不可用） |
| redteam/*.sh | 场景编号 | 0 用例按预期被拦下；非 0 发现漏洞 | 结构化结果文件（归档用） |

### 4.3 Makefile 分工

Makefile 只做薄封装：目标路由、参数透传、目录约定；一切逻辑在 scripts/。例：make up 等价于调用 env-up.sh 并透传参数。禁止在 Makefile 里写安装步骤与判断逻辑——那会导致 CI 与本地出现"第二份实现"（附录 B-4 的红线）。

## 5. 错误处理与失效语义

| 错误类别 | 检测手段 | 处置策略 | 姿态与理由 |
| --- | --- | --- | --- |
| 前置缺失（docker 未起、二进制版本不符版本表） | 启动校验 | 退出码 2，输出补齐指引 | fail-fast |
| 步骤超时（组件不就绪） | 轮询超时 | 退出码 3，输出该组件诊断包 | 超时即失败，不无限等 |
| 环境不可用（集群不存在却要求操作） | 现状检测 | 退出码 4，提示先 make up | 幂等纪律 |
| 通用失败 | errexit 捕获 | 退出码 1 + 诊断包 | 失败要响（I10 同源） |
| runsc 不可用 | 冒烟退出码 | 按 `deploy/kind/README.md` §4.6 降级链继续并显式标注 | 唯一的显式降级：沙箱是环境能力非放行判断，但摘要必须可见 |
| 红队用例"未拦下攻击" | 用例断言 | 脚本非零（发现漏洞），结果文件归档 | 红队脚本的非零是发现而非故障，语义与工程脚本相反 |

所有姿态均为 fail-fast 或显式降级——脚本层不存在"静默继续"。

## 6. 可观测性（日志 / 指标 / Trace / 审计）

- **结构化日志字段**：ts、level、script_name、step、component、version、action、result、duration_ms、error_class、hint。
- **指标**：`aegis_script_run_total{script, result}`、`aegis_script_duration_seconds{script}`。
- **审计留痕点**：熔断/降级的人工复位必须经脚本或 CLI 显式操作并留痕（F7 口径）；红队脚本每次执行产出可归档结果文件（时间戳 + 场景编号 + 结论 + 整改链接）；环境重建摘要归档 logs/（`deploy/README.md` §6）。

## 7. 依赖方向与模块边界

- **谁调我**：根 Makefile（薄封装）、CI workflow（同一份脚本）、开发者手动执行。
- **我调谁**：`deploy/` 下配置（kind 配置、组件清单）、`deploy/versions.md`、外部二进制（docker/kind/kubectl/helm）。
- **禁止依赖谁**：不内嵌 `internal/` 业务逻辑（脚本只编排环境）；禁止携带真实凭据（Langfuse key、LLM API key 只经环境变量注入）；**放行判断永不进脚本**——脚本只搭环境，裁决永远在闸门（设计文档 §4.1 职责边界的脚本侧表达）；同一份逻辑禁止在 CI workflow 里写第二份（附录 B-4）。

## 8. 测试策略与红队用例

- **幂等测试**：env-up/env-down 连续执行两次结果一致（T0.2 完成判据）。
- **出口自检**：W2 的 make up 全绿 + runsc 冒烟（Phase 0 出口标准，落地方案 §3）。
- **CI 同源测试**：kind-smoke.yml 调用同脚本，验证裁决一致（附录 B-3）。
- **红队纪律**：`redteam/` 下每个脚本本身即攻击载荷，入库前过安全审查；红队检查点 #2（M2 末，项目准入门槛）的五个用例（审批绕过/日志注入/越权/重放/预算绕过）必须全部脚本化、可重复跑（T2.13 与纪律 R-7 的共同要求）；`demo/` 与 `redteam/` 分离——前者面向验收口径（设计文档 §7 M2 三连），后者面向攻击视角，互不混用。
