# docs/adr — 架构决策记录（ADR）规范与索引

> 所属层：档案层 ｜ 里程碑：T0.6 建目录（落地方案 T0.6），M1 末首次复评 ｜ 设计文档出处：附录 A（ADR-001/002 体例）、§4.2.3、§4.3 ｜ 关联不变量：I6（决策可留痕、可回放的档案侧）｜ 关联失败模式：F10（过拟合 / 自证的姊妹纪律：决策可追溯）

## 1. 设计初衷

单人项目里，真正的风险不是"没做决策"，而是"做过决策但忘了、之后被静默推翻"。ADR 解决三类问题：

1. **防静默翻案**：形态级分歧（直写 vs PR、二开 vs 自研）一旦拍板就落盘，后续会话不得在没有新 ADR 的情况下改道——落地方案纪律 R-5（Non-Goal 拦阻）要求"要突破先写 ADR 进 docs/adr/，再动手"。
2. **保留叙事升级空间**：ADR-002 把"降级为自研薄运行时"写成带触发条件的备选，差异化叙事（设计文档 §9 末行 / 红队 R8）因此有据可查，而不是临场编故事。
3. **支撑复盘与复评**：每个里程碑末尾固定复评（落地方案 §2 纪律 R-7 的配套动作），复评结论直接追加进 ADR，决策寿命全程可见。

## 3. 技术选型与开源包

纯 Markdown，无工具链依赖。文件命名与存放规则：

1. 文件名 `ADR-0NN-<kebab-slug>.md`：三位零填充编号 + 短横线连字符标题 slug（如 `ADR-001-r1-direct-write-vs-r2-gitops-pr.md`）。
2. 一文件一决策；编号递增不复用，废弃决策保留原文、状态改 superseded。
3. 编号可以预留：预留位建空壳文件，头部 `status: reserved`，正文写明等待什么输入再补齐（见索引表 ADR-003）。

## 4. 具体设计（不写代码）

**ADR 模板**（五段式，体例照录设计文档附录 A 的 ADR-001/002）：

1. **背景**：分歧是什么、两边各长什么样、为什么现在必须拍板。
2. **决策**：拍板内容一句话说清，含适用范围（如"R1 直写、R2 强制 PR、R3 硬拒"的三级分界）。
3. **代价与接受**：明确承认放弃了什么、为什么仍值得（ADR-001 范例：接受 R2 交互断裂，换审计与回滚的确定性）。
4. **反方意见留档**：落选方案不删除，写明它会在什么条件下复活。
5. **复评触发条件**：写死什么信号出现就必须重审本决策（ADR-002 范例：kagent 上游架构剧变或 fork 维护成本 >20h/月）。

**编号规则**：从 ADR-001 起递增；superseded 不回收编号；reserved 占位允许存在但索引表中必须注明等待输入。

**每里程碑复评纪律**：

1. 复评时机固定为里程碑末尾红队检查点同一周（落地方案 §2 纪律 R-7、§4/§5/§6 末尾固定动作），不压缩、不挪用。
2. 复评结论三选一：维持（追加一句"某年某月复评维持"）、触发降级 / 备选（转第 3 步）、superseded（立新 ADR 承接，旧文状态改 superseded 且互相挂链接）。
3. 复评记录追加在原文末尾"复评记录"小节，历史结论不删不改——这与威胁模型红队记录表同一追加制（docs/README.md 第 6 节）。
4. 复评不是走过场：触发条件命中而未复评的，视为该里程碑收尾未完成。

## 5. 错误处理与失效语义

| 错误类别 | 检测手段 | 处置策略 | 姿态与理由 |
| --- | --- | --- | --- |
| 决策被静默推翻（代码已改道、ADR 仍 accepted） | 里程碑复评对照；PR review 时查索引表 | 立即补复评：改道合理的走 superseded 立新 ADR，改道不合理的回滚代码 | fail-closed：发现即冻结相关后续开发，先补档再说 |
| 复评跳票（里程碑收尾时未逐项过） | 里程碑收尾 checklist 固定项 | 该里程碑不算收尾；与红队检查点同等待遇 | fail-closed，同 R-7 纪律 |
| 编号冲突 / 孤儿预留位长期不补齐 | 索引表核对；W 级碎片时间抽查 | 编号冲突当场重排；reserved 超一个里程碑未动者降级为"作废预留"并记录原因 | — |
| ADR 质量注水（决策写了、代价与反方空着） | 模板五段完整性检查 | 打回补全；五段缺一段即不合入 | — |
| 与威胁模型 / 设计文档矛盾 | 文档同步纪律映射表（docs/README.md 第 4 节） | 以设计文档为事实源修正 ADR，矛盾消除前相关 PR 不合入 | — |

## 6. 可观测性（日志 / 指标 / Trace / 审计）

ADR 自身就是审计对象，审计面落实到具体字段与位置：

1. 头部五元组字段（`adr_id` / `status` / `date` / `supersedes` / `review_due`）是唯一状态源，索引表只镜像不新增状态。
2. 正文末尾固定两小节："复评记录"（逐次追加：日期 + 结论 + 触发信号）与"修订历史"（日期 + 一句话变更）。
3. 索引表列 `状态` 变更当日完成；superseded 链双向可追（旧文挂新号、新文挂旧号）。
4. 里程碑复评统计 `adr_review_lag`（应复评未复评条数），> 0 时里程碑收尾流程不通过——与 threat-model.md 的 `doc_lag_items` 同口径（docs/README.md 第 6 节）。

- **禁止依赖谁**：不反向约束代码实现细节（接口与字段细节归各 `internal/<context>/` 目录文档）；不依赖 `deploy/versions.md` 具体版本号；不收录代码级决策（那是 review 的事，不是档案的事）。

## 8. 测试策略与红队用例

- **入库判据**：T0.6 完成判据为 ADR-001/002 落盘（落地方案 §3）；Phase 0 出口标准含此项。
- **红队用例**（随各里程碑检查点执行）：
  1. R-5 拦阻测试：模拟一次"想突破 N3 加 Web 控制台"的冲动，验证流程是否先落到 docs/adr/ 再动手；
  2. ADR-002 降级演练：M1 末统计 kagent 集成实际耗时与阻塞点（落地方案 §4 固定动作），验证复评是否产出可执行的降级判断而非含糊其辞；
  3. 翻案侦测：对照 git 历史抽查一个形态级改动，验证其背后是否有对应 ADR 且状态正确；
  4. 注水侦测：随机抽一份 ADR，验证五段齐全、反方意见不是空话。
