# docs — aegis 文档体系总入口与档案层规范

> 所属层：跨层（决策层 / 执行层 / 档案层）｜ 里程碑：M1–M4 全程 ｜ 设计文档出处：§3.2（docs/ 目录定位）、§8.3 ｜ 关联不变量：I6、I8 ｜ 关联失败模式：F10

## 1. 设计初衷

aegis 是单人 + AI 辅助的安全敏感项目，bus factor = 1（落地方案 §10）。所有设计判断必须落在文档里，不留"只在脑子里"的决策；AI 会话之间没有共同记忆，换会话、换时段、换模型开发时，唯一的事实恢复手段就是文档。docs/ 目录由此承担两个硬职能：

1. **决策留档**（`docs/adr/`）：形态级架构分歧的永久档案，防止已拍板的取舍被静默推翻（落地方案纪律 R-5）。
2. **威胁档案**（`docs/threat-model.md`）：攻击面与缓解的映射底账，红队检查点的更新载体（设计文档 §10 的维护落点）。

差异化叙事钉死在 L2 安全闸门与 L4 eval 层（设计文档 §1.5），这两层的可信度不靠口头声明，而靠 ADR（为什么这么设计）与威胁模型（防住了什么、红队查出了什么）共同构成的证据链。

## 2. 职责与任务清单

**三层文档体系分工**（本目录是第三层）：

| 层 | 文件（仓库根相对路径） | 回答的问题 | 修改时机 |
| --- | --- | --- | --- |
| 决策层 | `AI原生K8s安全操作平台-技术方案设计文档.md` | 做什么、不做什么、为什么（目标 G、不变量 I、架构、数据契约、失败模式 F） | 里程碑级评审 |
| 执行层 | `AI原生K8s安全操作平台-落地方案-v1.0.md` | 谁先谁后、每周干什么、怎么算干完（T 编号任务、周排期、验收口径） | 里程碑验收后复评（§12 触发条件） |
| 档案层 | `docs/adr/`、`docs/threat-model.md` | 拍过什么板、怕什么攻击、红队发现过什么 | 随决策与红队即时更新 |

**docs/ 目录构成**：

| 路径 | 定位 |
| --- | --- |
| `docs/README.md` | 本文件：文档体系总述与同步纪律 |
| `docs/adr/README.md` | ADR 规范、编号规则、索引表 |
| `docs/adr/ADR-0NN-*.md` | 单条架构决策记录 |
| `docs/threat-model.md` | 威胁模型正文（红队维护） |

**任务清单**（对应落地方案 T0.6 及设计文档 §8.1 的文档账 30–40h，摊入每周碎片 1–2h）：

1. T0.6：`docs/adr/ADR-001.md`、`docs/adr/ADR-002.md` 转录设计文档附录 A；`docs/threat-model.md` 骨架入库（资产 / 攻击面 / 攻击者画像三节先行，正文 M2 前补齐）。
2. 每个里程碑末尾红队检查点后：更新 threat-model.md 的红队评审记录表与攻击面清单。
3. 每次新增 ADR：同步更新 `docs/adr/README.md` 索引表；若属设计决策变化，按落地方案 §12 第 2 条触发落地方案修订。
4. 每周碎片时间：对照当周代码变更核对文档漂移，发现应改未改条目记入待办。

## 3. 技术选型与开源包

纯 Markdown，无工具链依赖、无构建步骤。约定三条：

1. **命名**：目录说明文件用 `README.md`；正文档案用语义名（`threat-model.md`）；ADR 用 `ADR-0NN-<kebab-slug>.md`（规则见 `docs/adr/README.md` 第 4 节）。
2. **引用**：设计决策引用统一写作"设计文档 §x.y"；执行任务引用写作"落地方案 T?.?"或"落地方案 §x"；文件互引一律仓库根相对路径（如 `internal/risk/README.md`、`deploy/versions.md`、`.agents/skills/aegis-security-review/SKILL.md`）。
3. **修订留痕**：每份文档文末固定维护"修订历史"小节（日期 + 一句话变更），等价于审计日志，只追加不删改。

## 4. 具体设计（不写代码）

**三层职责边界细则**：

- 决策层是"宪法"：不变量 I1–I10、非目标 N1–N6、失败模式 F1–F15 只在设计文档定义，档案层只引用编号不重述全文。
- 执行层不做新决策（落地方案 §1 文档定位）：凡与设计文档冲突以设计文档为准；档案层发现执行层与设计层矛盾时，以设计层为事实源并当场标注。
- 档案层不回写决策层正文：发现设计文档疑似有误，先修订设计文档（走其自身的评审纪律），ADR 只记录其结果。ADR 可以 supersede 另一条 ADR，但无权修改设计文档章节。

**文档与代码同步纪律**（落地方案 §12 同款要求在文档侧的执行化，"改行为必改文档"）：

| 触发情形 | 必须同步的文档 |
| --- | --- |
| 新增 / 修改 CRD 字段 | 对照设计文档 §5 同步；威胁模型资产清单按需更新 |
| 改变分级、审批、回滚行为 | 对应 ADR 增订或新增；threat-model.md 缓解映射表更新 |
| 新增写工具 | 按 `.agents/skills/aegis-security-review/SKILL.md` 写工具准入第 5 条同步攻击面 |
| 新增组件或外部依赖 | ADR（若为形态级决策）；版本号一律写"以 `deploy/versions.md` 钉死为准"，禁止在文档里写死版本 |
| 里程碑验收 / 红队检查点 | threat-model.md 红队评审记录表追加；`docs/adr/README.md` 复评状态更新 |

## 5. 错误处理与失效语义

文档体系自身的失效模式与处置（这是档案层的"故障面板"）：

| 错误类别 | 检测手段 | 处置策略 | 姿态与理由 |
| --- | --- | --- | --- |
| 文档漂移（代码已改、文档未改） | PR 模板 I1–I10 对照勾选时人工发现；里程碑复评逐节核对；周碎片维护待办 | 阻塞合并或限期补更；涉及 I1 / I4 / I5 / I9 语义的漂移按 P1 记入红队评审记录 | fail-closed：拿不准就当漂移处理，回查必读材料后再放行 |
| 事实源冲突（档案层与决策层矛盾） | ADR 复评；索引表与正文对照 | 以设计文档为事实源；ADR 标 superseded 并立新 ADR 承接 | — |
| 决策只存在于会话上下文（未落盘） | 落地方案 §10 bus factor 行自检；每周维护核对 | 48h 内补 ADR 或威胁模型条目，逾期视为技术债记账 | — |
| 威胁模型过期（新攻击面未登记） | 红队检查点逐条对照；新写工具准入清单核对 | 检查点不算通过；M2 检查点是项目准入门槛（设计文档 §9），威胁模型未更新 = 门槛未过 | fail-closed，与闸门 I10 同构：档案缺失不静默放行 |
| 修订历史断档（只改正文不留痕） | 文末修订历史小节抽查 | 补录条目并注明补录原因 | — |

## 6. 可观测性（日志 / 指标 / Trace / 审计）

文档体系无运行时遥测，审计等价机制如下，全部落实到具体字段：

1. **ADR 结构化字段**（每个 ADR 文件头部固定五元组）：`adr_id`（编号）、`status`（proposed / accepted / superseded / reserved）、`date`（定稿日期）、`supersedes`（取代的前序编号，可空）、`review_due`（下次复评触发条件摘要）。
2. **修订历史**：每份文档文末固定小节，格式"日期 + 版本 + 一句话变更"，追加制。
3. **红队评审记录表**：threat-model.md 第 6 节逐次追加，历史行不删不改；整改落点列必须写清回写的设计文档章节号。
4. **门禁等价指标**：里程碑复评时统计 `doc_lag_items`（应改未改文档条目数），> 0 不进下一阶段；该指标口径为"当周代码变更映射表中应有同步而未同步的条数"。
5. **索引表即审计面**：`docs/adr/README.md` 索引表是全部决策的状态总览，任何状态迁移（accepted → superseded）必须当日完成。

## 7. 依赖方向与模块边界

- **谁调我**：仓库根 `README.md`、设计文档、落地方案（T0.6、§12、§10）引用 docs/ 下文件；`.agents/skills/aegis-security-review/SKILL.md` 的写工具准入与红队纪律要求读写 threat-model.md；PR 模板要求 ADR 链接。
- **我调谁**：docs/ 只引用仓库根两份主文档与 `.agents/skills/` 四个项目规范；ADR 正文引用设计文档章节号；不写任何实现代码，不被 Go import（落地方案附录 A：eval/ 与 docs/ 均不参与 Go 依赖方向约束）。
- **禁止依赖谁**：不引用 `deploy/versions.md` 的具体版本号（只引文件名，具体版本以钉死表为准）；档案层不得反向成为设计文档的审批者——设计文档变更无需 ADR 批准；docs/ 不发明主文档没有的组件名与功能（事实纪律见设计文档 §1.5）。

## 8. 测试策略与红队用例

- **入库判据**：T0.6 完成判据为"文件入库，纳入每周碎片维护"；Phase 0 出口标准含文档初始化项（落地方案 §3）。
- **里程碑复评检查**：每次红队检查点把"文档同步度"列为固定检查项——攻击面清单与当里程碑新增能力逐条对照，ADR 索引与当里程碑实际决策逐条对照。
- **文档侧红队用例**（自查用，纳入 M1–M3 各检查点）：
  1. 故意提交一份只改行为不改文档的假想变更，验证同步纪律第 4 节映射表能否在 review 时拦下；
  2. 编造一个未登记的攻击面（如"审批 Webhook 端点被仿冒"），验证 threat-model.md 的攻击面清单是否漏项、缓解映射是否有空档；
  3. 检查是否存在"accepted 状态但正文已被现实推翻"的僵尸 ADR，验证复评纪律是否执行到位。
